# Unit Test Skill

## 概述（Overview）
本Skill應根據以下原則撰寫單元測試:
- 開發者提供對應的`Gherkin`規格，並根據對應規格撰寫單元測試。
- 於`instruction`中有明確規範一定需要撰寫單元測試的對應範圍，則根據`需求文件`分析後，撰寫對應的單元測試，例如:如果要求controller 層必須有單元測試，則應撰寫對應的controller層測試。
- 如果`instruction`中沒有明確規範需要撰寫單元測試的範圍，則依據既有專案慣例與需求文件分析，撰寫必要的單元測試。


### 單元測試的範圍（Unit Boundary）

單元測試定範圍，根據以下說明:

1. 根據單元職責與可觀察需求界定測試邊界，包含`函式`、`物件`或`模組`，並非每個方法都需要有一份測試報告，重點在於涵蓋單元的主要行為與需求。
2. 進行單元測試時，相關邊界需要為自身可控制的範圍，避免依賴外部系統的真實行為，應使用替代方案如`Mock`、`Stub`或`Fake`。
3. 驗證真實行為應由`整合測試`或`End-to-End（端對端）測試`執行，單元測試僅專注於自身職責或可觀察需求。


### 技能組合與責任邊界

| 責任 | 對應規範 |
|---|---|
| 測試邊界、案例設計、預期結果、隔離、替身及斷言策略 | Unit Test Skill |
| 程式語法、型別、模組、檔名與語言特有的資源生命週期 | 所選語言 Skill 或專案規範 |
| 元件、框架生命週期與框架特有行為的測試方式 | 所選框架 Skill 或專案規範 |
| 測試工具、執行指令、報告、覆蓋率門檻與 CI 設定 | 專案規範或相關工具 Skill |

此Skill只定義單元測試的原則、範圍、設計與實作規範，不指定特定語言、框架或工具的使用方式，相關語言規範由所選語言 Skill 或專案規範決定。

## 核心原則（Core Principles）

### 開發優先遵守規則

- 可觀察需求優先於內部實作細節。
- 有意義的斷言優先於測試數量與覆蓋率數字。
- 可重複與互相獨立優先於依靠環境巧合通過。
- 控制必要邊界優先於替換全部依賴。
- 清楚的案例意圖優先於過度抽象的測試工具。
- 需求與風險優先於固定數量的測試案例。

### 允許與建議使用

- 從已確認需求、公開需求與缺陷重現條件設計案例。
- 驗證回傳結果、對外可觀察狀態，以及需求要求的副作用。
- 使用正常、邊界與失敗情境檢查重要行為。
- 對時間、亂數與外部服務使用可控制的替代來源。
- 保留純計算、簡單資料物件與合適的內部協作者的真實實作。
- 同一行為有多組資料時，使用工具支援的參數化案例。
- 修正缺陷時，依需要加入能防止相同行為回歸的測試。

### 禁止或應避免的使用方式

- 不使用待測程式產生自己的預期答案。
- 不把待測演算法原樣複製到測試中當成判定依據。
- 不以「執行完沒有例外」代替應有的結果斷言。
- 不只因依賴存在就將它全部 Mock。
- 不預設斷言私有方法、內部資料結構或無需求意義的呼叫順序。
- 不讓測試依賴其他案例的執行順序或殘留狀態。
- 不用固定等待時間、無限重試或跳過測試掩蓋不穩定行為。
- 不為增加覆蓋率而建立沒有行為判斷的測試。
- 不為方便測試而擴大公開介面、移除驗證或降低正式程式的正確性。


## 測試規範（Test Standards）


### 測試案例來源（Test Case Sources）

1. 開發者會根據需求文件設計出對應的`Gherkin`規格，作為單元測試案例的依據；如果開發者提供的對應情境不完整時，應補充缺少的情境以確保測試涵蓋所有重要行為與需求。
2. 開發過程中，根據實際程式行為與觀察到的邊界情境，補充或調整測試案例，以確保測試涵蓋所有重要行為與需求。

### 命名規範（Naming）

1. 如果為開發者提供的`Gherkin`規格，應沿用其情境描述與命名方式，並且需要進行註解確認相關來源，以利後續追蹤與維護。
2. 如果非開發者提供，而是透過`需求文件`進行設計的測試案例，則不需要沿用`Gherkin`規格的命名方式，但相關測試名稱應說明情境、行為與預期結果。
3. 避免只使用「測試一」、「正常情況」或待測方法名稱，讓失敗報告無法辨識行為。

建議：

```text
總額等於免運門檻時，計算運費應回傳零
餘額不足時，扣款應失敗且保留原有餘額
同一請求重複送達時，應保留第一次處理結果
```


### 安排、操作與斷言（Arrange / Act / Assert）

使用清楚的測試結構，不強制加入三個區段註解；程式已清楚表達時可省略。

```text
案例：餘額不足時拒絕扣款

安排（Arrange）：
  建立餘額為 100 的帳戶

操作（Act）：
  嘗試扣款 150，觀察失敗結果

斷言（Assert）：
  失敗原因為「餘額不足」
  帳戶餘額仍為 100
```

一個案例聚焦一個行為，但可以使用多個斷言檢查該行為的完整需求。不要求「每個測試只能有一個斷言」。

若行為本身是一段狀態轉移，可以安排必要的操作序列；不同且互不相關的行為應分成不同案例。

### 斷言設計（Assertions）

| 需求內容 | 適合驗證的觀察 |
|---|---|
| 計算結果 | 明確的回傳值或結構 |
| 狀態變化 | 對外可觀察的新狀態與應保持不變的狀態 |
| 拒絕操作 | 可區分的失敗結果，以及未發生的不允許副作用 |
| 對外輸出 | 發出的訊息、事件或寫入內容 |
| 協作限制 | 需求明確要求的呼叫次數、順序或冪等性 |

斷言需能區分正確與錯誤行為。僅檢查結果存在、不是空值或屬於某個型別，通常不足以驗證具體計算與業務規則。

不建議：

```text
操作：計算總額
驗證：結果有值
```

建議：

```text
前提：兩件商品各為 120，無折扣且不含運費
操作：計算總額
驗證：總額為 240
```

依需求決定順序、精度與比較範圍。沒有順序保證的資料，不任意要求固定順序；數值容許誤差需有領域依據，不用任意放大的容許範圍讓錯誤通過。

錯誤訊息只有在文字本身是公開需求時，才完整比對；一般情況優先檢查可區分的錯誤種類或內容。

### 邊界與失敗情境（Boundary and Failure Cases）

須根據需求挑選適合的邊界與失敗情境，避免使用同一種固定模式。

| 類型 | 可評估的情境 |
|---|---|
| 數值限制 | 最小值、最大值、恰好等於門檻、剛好超出範圍 |
| 集合 | 空集合、一個元素、多個元素、重複資料 |
| 必要輸入 | 未提供、格式錯誤、違反業務規則 |
| 狀態轉移 | 允許的轉移、禁止的轉移、重複操作 |
| 外部失敗 | 拒絕、逾時、不可用或不合需求的回應 |

空值的表示方式、數值限制與錯誤機制由實際語言及需求決定，不預設所有語言都有相同的 null、undefined 或例外行為。

失敗案例需確認錯誤確實被觀察與驗證；如果操作意外成功，測試應失敗。避免捕捉錯誤後無條件通過。

### 測試資料與 Fixture

測試資料以表達該案例所需的最少資訊為原則，保留讓案例成立的必要欄位。

- 建立名稱清楚、有效的基礎資料，讓案例只覆寫與情境有關的值。
- 避免龐大且缺乏意義的共用資料，迫使讀者理解整個系統。
- 可共用不可變的資料或資料建立邏輯；每個測試使用自己的可變狀態。
- 不為簡單案例建立複雜的資料產生器或抽象層。

### 測試替身（Test Doubles）

依需要控制的邊界選擇替身，不要求 Mock 所有依賴。

| 類型 | 用途 |
|---|---|
| Dummy | 只滿足介面或呼叫需求，不參與該案例行為 |
| Stub | 提供案例需要的固定回應或失敗結果 |
| Spy | 記錄對外互動，供必要的斷言使用 |
| Mock | 定義並驗證需求需要的協作期待 |
| Fake | 提供簡化但能運作的替代實作，例如記憶體中的儲存邊界 |

依用途理解替身，不因工具把物件命名為 Mock，就假設必須驗證每個呼叫。

時間、識別值、亂數、外部服務或持久化邊界，需要控制時可替換。純計算與簡單內部協作者通常可以保留真實實作。

不建議：

```text
替換訂單服務內的每個方法
指定每個私有步驟的回傳值
驗證它們按照目前實作的順序被呼叫
```

建議：

```text
前提：庫存邊界回報無庫存，使用可觀察的儲存替身
操作：呼叫真實訂單服務建立訂單
驗證：結果為無庫存，儲存邊界未新增訂單
```

在替身控制的邊界之外保留真正的待測行為。不能將待測單元本身的核心行為替換掉，再以替身回應證明它正確。

### 可測試性（Testability）

既有程式難以控制外部因素時，先尋找現有介面或可替換邊界。必要時，在需求範圍內加入小幅且有明確價值的接縫，例如可提供固定時間的時鐘來源。

不為測試匯出私有方法、改變正式行為或建立不必要的架構層。若需要大幅改造才能完成測試，先說明限制與影響。

### 隔離與可重複性（Isolation and Determinism）

測試的結果不應由其他案例、執行順序或環境巧合決定。

- 每個案例建立自己的待測狀態及可變替身。
- 還原修改過的全域狀態、環境設定與替代來源。
- 不共用未隔離的識別值、連接埠或可寫入資源。
- 即使斷言失敗，也要透過工具的生命週期機制清理資源。
- 是否平行執行依資源與測試環境決定，不強制全部串行或全部平行。

需要時間或亂數時，使用可控制且可重現的來源。時區、地區與日期格式只在需求相關時納入案例，不依賴執行機器的預設值。

### 非同步與時間（Async and Time）

非同步是待測行為的一部分時，等待明確的完成結果或可觀察條件，再進行斷言；等待方式依語言及工具決定。

不建議：

```text
啟動非同步工作
等待固定 2 秒
假設工作已完成並檢查結果
```

建議：

```text
啟動非同步工作
等待可控制的完成訊號
驗證工作結果與後續狀態
```

等待應有合理的逾時上限，讓未完成的工作能明確失敗；逾時上限不取代完成條件，也不透過任意放大上限掩蓋問題。

計時、重試或到期行為，優先用可控制的時鐘或計時機制推進，不讓測試實際等待很長時間。

不要讓測試在工作尚未完成時結束。錯誤、取消與清理必須能被觀察；若語言不支援某種結果機制，依其可用需求實作，不假設一定使用 Promise 或例外。

真正的競態情境使用可控制的執行進度重現；不藉由放大等待時間或強制串行來假裝已驗證併發正確性。

### 參數化與性質測試（Parameterized and Property-based Tests）

相同行為搭配多組輸入時，可以使用既有工具支援的參數化測試。案例名稱需辨識輸入與預期差異，每組資料保持必要的狀態隔離。

不以複雜迴圈混合多個不同職責，讓第一個失敗掩蓋後續情境。

待測需求具有明確不變條件時，可以考慮性質測試，例如排序結果保持原有元素，且符合指定順序。不變條件必須足以指出有意義的錯誤；只有「沒有拋出錯誤」通常不夠。

使用產生式資料時，限制有效輸入範圍，保留可重現失敗的種子或最小案例。不為使用這種方法另行導入沒有必要的工具。

### 快照（Snapshot）

快照適合穩定、需要比較整體結構的公開輸出。巨大、包含不穩定值或沒有明確審查方式的快照，不應取代具體行為斷言。

快照變動時，先確認變動是否符合需求，再更新；不將重新產生快照視為測試修復本身。

### 覆蓋率與回歸（Coverage and Regression）

覆蓋率用於尋找未執行的程式區域，不證明斷言有效、需求完整或結果正確。

優先補足重要需求、邊界、失敗與已知缺陷的回歸案例。是否設定百分比門檻依專案要求，不自行預設所有專案都須達到相同數字。

修正缺陷時，若需要回歸測試，先確認案例能區分原本錯誤與預期行為。可行時在隔離範圍內確認它會因相同行為錯誤而失敗，不操作正式環境來重現缺陷。

不為通過測試而降低斷言、跳過相關案例或修改預期值以迎合錯誤實作。

## 驗證與交付（Validation and Delivery）

先執行與變更直接相關的測試；再依修改範圍執行必要的相鄰測試、既有檢查或專案要求的測試集，不固定要求每次修改都執行全部測試。

發生失敗時，區分需求變動、測試錯誤、正式程式錯誤與環境問題。既有無關失敗應清楚記錄，不以它為理由略過相關驗證。

必要時確認以下事項：

- 相關行為錯誤時，測試是否會失敗。
- 個別執行與合理的不同順序下，結果是否一致。
- 測試是否真正被發現、執行並包含有效斷言。
- 替身是否保留真正的待測行為。
- 測試失敗後是否仍能清理資源。

不穩定測試需定位原因，不反覆重跑直到偶然通過。尚未確認原因時，如實回報不穩定狀態。

交付時說明測試所驗證的需求、重要案例與實際執行結果。明確區分通過、失敗、跳過與未執行；未執行時提供原因，不將靜態檢查或推測當成測試已通過。
